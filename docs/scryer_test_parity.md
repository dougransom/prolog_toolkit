# Scryer Compatibility & Parity Guidelines

This document outlines the principles, approximation guidelines, and development workflow for verifying compatibility and parity with Scryer Prolog and its standard library.

---

## 1. Approximation & Compatibility Principles

1. **Syntactic & Functional Compatibility**:
   - Compatibility does not need to be 100% exact in internal engine quirks, but must be logically correct, close, and syntactically compatible.
   - Target queries should produce equivalent logical results, variable bindings, and standard exception terms.

2. **Lexical Conventions**:
   - Aim for the same lexical and structural conventions (e.g. whitespace handling, operator formatting, character list representations).
   - **Pragmatic Pragmatism / No Kludges**: Reasonable exceptions can be made when matching exact formatting requires brittle hacks or awkward kludges. Clean, pure Prolog logic takes precedence.

3. **Pure ISO & Scryer Prolog Standards**:
   - **Strings**: Double-quoted strings are always lists of characters (`chars`).
   - **Type Checks**: Prefer `library(si)` (e.g. `atom_si/1`, `list_si/1`, `integer_si/1`).
   - **Purity & Conditionals**: Use `library(reif)` (`if_/3`, `dif/2`). Prefer `if_/3` over non-pure cuts `->` where applicable.
   - **Style Pattern**: When testing and generating a value for subsequent use, test and generate within the condition and consume the bound variable after the condition:
     ```prolog
     if_(Condition, Val = "A", Val = "B"),
     format("Value: ~s~n", [Val])
     ```
   - **Prohibitions**: Never use non-standard or SWI-specific features (e.g., `dicts`, string types, `is_list/1`).

---

## 2. Testing & Verification Workflow

1. **Incremental Single-Module Verification**:
   - When implementing or refining tests for each Scryer standard library module, **focus on getting that specific module working and verified individually** before moving to the next.
   - Use targeted targets:
     ```bash
     make test-scryer-<module>   # e.g., make test-scryer-lists, make test-scryer-clpz
     ```
   - Avoid running the entire end-to-end test suite on each small iteration to keep turnaround times fast.

2. **Dynamic Scryer Reference Generation**:
   - Test reference outputs are dynamically generated by Scryer Prolog into the build directory (`build/scryer_compatibility/<test_file>.scryer_out`) upon build / `make clean`, rather than maintaining rigid static string literals.
   - Tests execute via `nice scryer-safe` under dynamic resource and timing limits.

3. **Sandboxing & Environmental Constraints**:
   - Scryer testing runs under `scryer-safe` containment.
   - Modules requiring external operating-system permissions (e.g., unrestricted child process pipes in `library(process)`) should account for sandboxed environments or provide appropriate mock wrappers.
